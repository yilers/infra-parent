# 基础能力模块规划

`infra-parent` 在 UPM 之外规划文件、通知、工作流和短链等可复用能力。各能力采用 `api + core` 分层，统一部署由 `infra-start` 组装，需要独立部署时再增加各自的 `start` 模块。

## 模块边界

| 模块 | 定位 | 当前状态 |
| --- | --- | --- |
| `upm` | 租户、应用、用户、组织、RBAC、认证和 SSO | 已实现 |
| `file` | 文件上传、下载、存储和访问控制 | 规划中 |
| `notice` | 短信、邮件、钉钉和飞书通知 | 规划中 |
| `flow` | 流程定义、实例、任务和审批 | 1.2.0 开发中 |
| `shortlink` | 多租户短链配置、生成与跳转 | 1.2.0 开发中，见 [短链接入说明](../SHORTLINK.md) |

`common` 只承载通用技术能力，不放置具体业务模块的实体、服务和控制器。`api` 模块保存稳定的服务契约及请求响应对象，`core` 模块保存业务实现、持久化和 HTTP 接口。

## 部署方式

模块支持两种接入方式：

1. 模块集成：业务启动器直接依赖对应的 `core`，使用本地 Service 和同一数据库。
2. 独立部署：新增对应的 `start`，业务系统只依赖 `api`，通过 HTTP 或 RPC 调用。

`infra-start` 是基础能力统一部署入口，依赖 UPM、文件、通知、工作流和短链的 `core`。`upm-start` 继续作为 UPM 独立部署入口。当前不创建空的独立启动器，出现真实的独立部署需求时再创建启动器及远程适配器。

## 依赖约束

- `file-core`、`notice-core`、`flow-core` 不直接相互依赖。
- 三个 `core` 不直接依赖 `upm-core`，认证基础能力来自 `common-auth`。
- 需要用户、角色或部门信息时，通过模块自定义的扩展接口适配本地 UPM；独立部署时由组装层依赖 `upm-api` 实现远程适配。
- 第三方框架类型不得暴露到各模块的 `api` 中。
- HTTP 文件流不通过 Dubbo 等 RPC 接口传输，RPC 只传递文件标识和元数据。

## 数据规范

- 文件服务表使用 `file_` 前缀。
- 通知服务表使用 `notice_` 前缀。
- 工作流原生表使用 `flow_` 前缀，自定义扩展表使用 `flow_ext_` 前缀。
- 短链表使用 `shortlink_` 前缀；UPM 管理的通用系统调用凭证使用 `upm_api_credential` 前缀。
- 需要隔离的数据必须包含 `tenant_id`；需要区分应用的数据同时包含 `application_id`。
- 用户、租户和应用上下文由服务端登录态恢复，不信任客户端直接提交的身份请求头。

## 建设顺序

1. 完善 UPM 部门主管配置，为流程动态办理人提供可信组织关系。
2. 验证 Warm-Flow 与当前 Spring Boot、JDK、MyBatis-Plus、租户插件和官方 Vue 设计器的兼容性，再建设 OA 首期流程能力。
3. 文件与通知模块按实际业务需求建设；Flow 首期不强制等待二者实现。
4. 出现独立部署需求后再补充各模块启动器、服务间身份校验和 HTTP/RPC 适配。
