# 动态办理人配置

## 页面操作

经典模式、仿钉钉模式共用节点属性面板。进入审批节点的“办理人设置”，点击“选择办理人”，切换到“动态规则”页签，勾选需要的规则并确定。节点表格和画布回显规则名称，保存并重新打开后保留配置。

| 规则 | 实际存储的Warm-Flow表达式 | 后端处理 |
| --- | --- | --- |
| 申请人 | `${wfApplicant}` | 本次发起流程的已登录用户 |
| 本部门副主管（无则主管） | `${wfDepartmentApprovers}` | 查申请人所在部门的有效副主管；排除本人、无效账号后没有候选人时，查本部门主管 |
| 上一级部门主管 | `${wfParentDepartmentApprovers}` | 查申请人所在部门的直接上级部门主管，不是上一位审批人的上级 |

多个副主管任意一人通过，应在节点“基础设置”中选择“或签”。候选人规则只负责选人，不会强行覆盖设计器设置的会签、票签等协作方式。

固定角色、部门、用户仍按原方式选择；同一节点可选择多个办理项，表达式按引擎机制展开后合并。手动输入合法标识、离开输入框时回显名称；不认识的自定义变量不会在表格中被自动删除，但宿主必须自行提供变量，未解析的表达式不能生成有效任务。

## 规则边界

- 只在流程发起时解析该定义实际使用的内置规则；不使用部门规则的旧流程，无需配置主管。
- 申请人、租户、部门均由后端可信身份读取。没有有效部门、没有上级部门、没有有效主管时明确报错，不默认跳过或允许所有人办理。
- 主管任职按当前有效期查询；已删除、已停用、跨租户账号以及申请人本人不能成为这些主管规则的候选人。
- 申请人是副主管时，排除本人后仍有其他副主管则由其他副主管办理；没有则找本部门主管。主管本人申请且无人可兜底时阻止发起。
- 不自动跳过不同审批节点中的同一个审批人。是否需要去重审批，应由后续业务规则另行明确。

## 实现与安全

`flow-api` 定义 `WorkflowAssigneeRule` 和 `WorkflowIdentityProvider.resolveDynamicAssignees` 契约；`flow-core` 不依赖 `upm-core`。`infra-start` 的UPM身份适配器使用用户、部门、主管任职服务实现规则。独立宿主可实现同一接口，通过本地Service或远程服务获取组织数据。

`WorkflowAssigneeResolver` 在启动前读取当前租户已发布定义，按需要解析规则，将用户ID列表写入实例变量；Warm-Flow原生 `${变量名}` 机制解析为任务办理人。沿用现有权限适配和候选人校验，不另建审批引擎，也不要求用户填写监听器。

三个 `wf...` 变量为服务端保留变量，发起、通过和退回时，业务调用方不得覆盖。当前HTTP办理接口也不接受客户端修改流程变量。未解析的表达式和空候选人会导致事务回滚，不留下无人可办的任务。

本轮使用发起时的审批人快照：后续审批、退回再办理使用同一实例保存的变量，不根据当前审批人的部门重新选人，也不因组织调整自动换人。账号在后续流转时失效则由原有有效账号校验拒绝流转，应由管理员按实际业务处理，不自动找其他人替代。

实例只读图展示规则名称；当前任务和历史中的用户姓名展示仍属于独立的后续需求。

## 请假流程配置示例

1. 复制已有 `leave` 定义创建新版本，不修改已产生实例的旧版本。
2. 本部门审核节点选择“本部门副主管（无则主管）”，协作方式选择“或签”。
3. 下一个审批节点选择“上一级部门主管”，配置通过后结束。
4. 检查申请人所在部门及直接上级部门均已启用，相关主管任职有效且账号可用，然后发布新版本。

不需要增加数据库表、字段或执行SQL；内置规则作为既有节点 `permissionFlag` 保存，快照使用既有实例变量。

如果额外添加“申请人提交”普通办理节点，可选择“申请人”规则，退回路线指向该普通节点而不是开始节点。当前通用待办支持该节点的通过、按路线退回及再次办理，但**请假业务页面仍只允许编辑未提交草稿**：退回后编辑表单、首次提交自动完成申请节点、业务表单重新提交，尚未在本轮扩展。仅新增节点不会自动生成这些表单行为；现阶段会先产生申请人自己的待办，需要在“我的待办”办理后进入下一节点。

## 回归覆盖

引擎集成测试覆盖“申请人提交→本部门多人或签→上级部门主管→结束”，以及退回申请人后重新办理、保留原申请人审批配置、阻止覆盖保留变量、无有效候选人时不创建实例。UPM适配测试覆盖副主管优先、主管兜底、本人排除、停用账号过滤和跨租户部门拒绝。前端组件测试覆盖动态页签选择、表达式手填回显、经典及仿钉钉模式的保存与重新打开。
